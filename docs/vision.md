# Camera and calibration

## Selecting the camera on this host

`camera.backend` chooses the OpenCV capture backend. Left empty it resolves to AVFoundation on macOS and V4L2 on Linux; anything else falls back to `CAP_ANY`. This matters because V4L2 is Linux-only: requesting it on macOS opens nothing and the worker reports `Camera 0 unavailable; retrying` forever. Accepted overrides are `avfoundation`, `v4l2`, `dshow`, `msmf`, and `any`.

`camera.device` is an index, not a path. On a laptop the built-in camera usually takes index 0, so the Arducam is normally a later index. Run `uv run python -m beaver_battle --list-cameras` to see which indices open and at what resolution, then record the working one in ignored `config.local.toml` or pass `--camera N`. The probe opens and releases each index in turn and never opens a window.

On macOS the capture process needs Camera permission in System Settings > Privacy & Security > Camera, granted to the application that owns the terminal (Terminal, iTerm, or the editor). OpenCV requests the permission and fails the same call rather than waiting for the answer, so the first run after approving still reports the camera as unavailable; run it again. An application launched from a quarantined location such as `~/Downloads` runs under App Translocation from a randomized read-only path and cannot keep the grant at all; move it to `/Applications` and relaunch it first.

## Capture and mapping

The UVC capture thread requests MJPEG at the configured camera resolution and rate. It continually replaces one pending frame; the processing thread consumes the newest observation without a queue. Preview arrays are immutable BGR camera images. Aims and wall arrays are in logical display coordinates. Camera failures clear valid aims, report an error, and retry once per second; frames older than `camera.stale_seconds` never produce usable aim.

Keep the camera and projector fixed together. Show the calibration screen and include all four black ArUco markers (DICT_4X4_50 IDs 0–3) in the camera view. Their sixteen corners determine a camera-to-display homography. The saved `.npz` includes both camera and display dimensions and is rejected if either changes. Physical movement or projector keystone changes require calibration again even if resolution is unchanged. This is a planar mapping, not 3D object reconstruction.

While calibration is pending, the snapshot error names the corners the camera cannot see, for example `Show all four calibration markers; missing top-left, bottom-right`, so the mount can be aimed from the projected screen without reading the laptop. When all four are detected but the homography is still rejected, the message says so instead; that points at glare, motion, or a marker seen at too shallow an angle rather than at framing. Detection runs on a CLAHE-equalized grayscale image (`camera.marker_clip_limit`, `camera.marker_tiles`; set the clip limit to 0 to disable). A projector competing with room light can separate its own black from its own white by only a couple of dozen gray levels on the whiteboard, which plain adaptive thresholding cannot recover. Under that much noise individual markers also drop out from frame to frame, so a calibration attempt keeps each marker's most recent corners for `camera.marker_memory_seconds` and may assemble one mapping from several frames. This assumes a motionless rig: if the camera or projector actually moves mid-window the remembered corners come from different poses, and the existing five-pixel reprojection limit rejects the result instead of saving a wrong mapping. Remembered corners are discarded when calibration starts, succeeds, or is cancelled. Black marker detection needs a bright screen with visible white margins. Calibration images are not learned as walls; learning resumes half a second after successful calibration. `calibration.npz` is local machine data, not a repository artifact.

`Vision.cancel_calibration() -> None` cancels a pending request without deleting the existing mapping or saved calibration. It immediately restores the snapshot's calibrated status from the current usable mapping (False if none exists), clears aim output, and retains physical walls. A cancelled or superseded in-flight marker detection cannot save, replace the mapping, or publish a stale result. Wall learning waits half a second after cancellation so projected markers can clear. Calls are safe from the UI thread and may be repeated; each call renews the settling interval. A calibration already committed before cancellation remains valid.

# Physical drawings and projected art

Wall detection warps the camera image and then looks for ink, meaning pixels darker than the board immediately around them. A black-hat transform over a `camera.wall_stroke` kernel measures that local drop, and anything at least `camera.wall_contrast` below its surroundings counts. Pixels with **all three color channels below `camera.wall_threshold`** still count as well, which covers genuinely dark areas wider than the kernel.

The local test carries the work because an absolute cutoff cannot survive a projected surface. Measured on the mounted rig, glare moves the bare whiteboard between about 158 and 212 while a black marker stroke photographs near 150 once the lens blurs it against a lit background, so no single cutoff separates ink from board. The local drop at the same stroke reached 184 against a canvas-wide 99.5th percentile of 6. `wall_stroke` must exceed the widest stroke actually drawn, or the middle of a fat line reads as background; 21 logical pixels is roughly 2.5 cm on a 1.5 m board.

The strongest color channel is used, so saturated red ink stays reserved for laser dots and is not read as a wall.

`camera.wall_persistence` consecutive observations add a wall; the same number of contrary observations erase it. `camera.wall_update_hz` bounds update cost, and setting it to 0 keeps the calibration board scan without ever re-reading the board under game art. Published masks are bool arrays of `(display.height, display.width)`, True for solid. Bright frames or transient shadows shorter than the persistence interval do not immediately change walls. Longer shadows and hands can become temporary obstacles.

# Hands, shadows and props during play

Ink detection finds marks on the board. It cannot find a hand, because a hand is far wider than `wall_stroke`, so the black-hat sees at most its edge. Nor can absolute darkness find one: measured on this rig a hand sits only about nine camera levels below the board on the strongest channel, while the pastel palette moves individual channels by as much as 148. A hand blocking the beam and a deliberately dark sprite are the same picture.

The missing information is what the projector sent. `Vision.set_projection(canvas)` supplies it: the app hands over the frame it just drew, as an RGB array already in logical pixels, so no warping is needed. Calibration measures the projector's own strength per channel from the one screen that shows both extremes at once, its white field against its four black markers, and stores the board as it looks under that field. Together these predict what the camera should see:

    expected = reference - gain * (1 - canvas / 255)

Anything materially darker than that prediction is light something physically took away. `camera.obstacle_threshold` sets how much darker, and components below `camera.obstacle_min_area` are discarded so laser dots and sensor noise cannot become walls. Both sides are blurred, and `camera.projection_delay` selects the canvas that was actually on the board when the camera frame was taken, because projector latency would otherwise ring at every moving edge. The test is signed: erasing a drawing makes the board brighter than predicted and correctly adds nothing.

Handing over the canvas is optional. Without it the worker reports drawn ink only, which is what the headless checks and any non-pygame consumer do. The app reads the framebuffer at `camera.wall_update_hz` rather than every frame, since that read is not free.

Because artwork is now predicted away rather than merely outshone, the earlier constraint on projected art is gone: the palette may be as dark as it likes, and brightening the projector no longer erodes the margin. It widens it, since `gain` rises with it.

Measured on September 19, 2026 with a hand held in the beam: drawn ink alone held the board at 2297-2766 wall pixels, and a hand added between 8,000 and 32,000, appearing in the mask as a recognizable hand with separated fingers. A 22-sample control run with nothing in front of the projector produced a median of 84 and a peak of 170 excess wall pixels, 0.018 percent of the canvas, all of it thin-ink flicker below the component floor; the obstacle path contributed nothing at all. That is about a hundredfold separation. Hands entering from the edge of the board stay open regions rather than closed shapes, so they are solid without being filled or drawn as rocks.

# Reading the drawing at calibration

A successful calibration scans the board from the same frame that produced the mapping and publishes the result at once, so a drawing is solid the moment calibration finishes rather than after the persistence filter fills in. This frame is the cleanest read the rig ever gets, because the projector is showing the calibration screen's flat white field instead of game art. The four projected markers are dark by construction and are excluded from the scan with a `wall_stroke` margin. `WallFilter.seed` adopts the scan outright; a deliberate board read needs no repeat confirmation.

`game.py` turns ink into geometry: `closed_shapes` closes gaps up to `game.shape_gap`, fills any region fully enclosed by ink, and classifies each fill as a log or a rock by aspect ratio. A drawn outline therefore becomes a solid body, not just a solid line.

Projected on September 19, 2026 through `--display 1 --fullscreen --calibrate --bench 3`: the projector carried markers, calibration, countdown, and a live three-player match at 2653 frames in 45 seconds, about 59 fps, with the camera calibrated and delivering frames throughout. A board photograph taken mid-match and warped by that calibration put the game's wall contours on the physical ink, including a square drawn on the board after the circle. Phase-correlating the rendered canvas against that warped photograph placed projected art within 2.4 px of where the game drew it, which checks the projector-to-camera direction rather than only the camera-to-game one.

Measured end to end on September 19, 2026 with a circle drawn in black marker: calibration published 1449-1508 ink pixels, closed-shape filling turned them into about 14,500 solid pixels, and the result was classified as one rock at (493, 245) with a 132x129 bounding box. Driving a canoe straight at it for 900 frames, the hull closed to 84.9 px of the centre against a 65 px barrier radius and an 18 px hull, spent 11 frames in contact, and never overlapped the ink; it slid around the obstacle as wall forgiveness intends.

Projected art must avoid strong *local* darkness, not merely a dark average, since the ink test is a local one. The current pastel palette is comfortably clear: its darkest element is an outline at max channel 96 against a white background, which lands near 12 levels of local drop against a threshold of 30. This constraint applies to the ink path only. The obstacle path below predicts artwork away and is not subject to it.

Keep projected game art bright: at least one camera color channel must remain above the configured threshold. Avoid dark outlines, dark text, and black projected backgrounds during play. Projected red highlights the size of a laser are indistinguishable from physical red spots, so reserve small saturated red regions for lasers. Use blue, cyan, yellow, white, and sufficiently bright green for art. Actual exposure, wall threshold, and laser area limits require tuning on the mounted camera; software does not adjust exposure, gain, or white balance.

# Same-color laser identities

Detection finds red components in the original camera frame before transforming their centers. It rejects components outside the configured area limits and outside the logical display. The bridge calls `set_identity(player_id, ready_since)` only after commanding that controller's laser on and others off, receiving acknowledgements, and allowing camera settling. Frames received before `ready_since` cannot establish identity. Exactly one red component must be visible to initialize/reacquire that identity. `set_identity(None, ready_since)` resumes ordinary all-on tracking after settling.

Up to three established identities follow short-term motion via unique global assignment. Missing, merged, closely spaced, stale, or ambiguous dots become invalid. They can regain identity only through another acknowledged solo window; separating an overlap never silently guesses player identity. During an identification window, other controllers retain their internal track but publish no aim because their lasers are intentionally off. The game retains heading whenever no confident aim is present.

Both solo and all-on transitions require matching command-sequence acknowledgements before camera settling. A rejoining controller revokes readiness; a dropped controller's last possible on-command must expire before a solo frame can identify another player. All-on readiness leaves at least 150 ms for ordinary observations before the next probe. Tune `identity_window`, `identity_settle`, and `identity_interval` on the real network/camera: a slow probe can still exceed the 500 ms track freshness limit, causing conservative invalidation and reacquisition.

# Checks

Run `.venv/bin/python -m checks.check_vision` from the repository root. It uses generated frames and temporary calibration files and does not open a camera. It checks perspective marker calibration, missing-corner guidance, faint-projection recovery, multi-frame marker assembly and expiry, local-contrast ink detection against a glare gradient, marker exclusion and seeding in the board scan, obstacle detection under dark artwork with erasure and laser-dot rejection, projector gain measurement, projection handover and delay selection, host backend selection, calibration dimensions, cancellation during detection with/without an earlier mapping, obsolete-result rejection, post-cancel wall settling, laser extraction, three-player identity, overlap recovery, wall hysteresis and erasure, bright art, immutable/stale snapshots, latest-frame replacement under load, reconnect, and resource release. Synthetic passes do not establish physical tracking accuracy or projector latency.

Live smoke check on September 19, 2026: the connected Arducam returned 1280×720 BGR frames through this worker, with a most-recent-frame age of 20 ms at the sampled instant. Both threads stopped and the camera was released. Physical marker calibration, simultaneous laser tracking, and wall threshold tuning still require the mounted projection setup. A synthetic 1280×720 benchmark averaged 12.2 ms of processing per frame on the development laptop; this is not an end-to-end latency measurement.

Physical calibration verified on September 19, 2026, on the macOS laptop against the mounted Arducam (index 0) and the projector on display 1 at 1920x1080. Before the fix the V4L2 request opened no camera on macOS at all, and a `--calibrate` run had been sitting on the marker screen for about forty minutes without ever reading a frame. After it, the `Vision` worker calibrated in 3.2 seconds, saved the `.npz`, and reported no error. Warping that camera frame by the resulting matrix put all four markers on their nominal `marker_layout` positions in the 1280x720 canvas within 1-6 px of round-trip corner error, and the projected caption landed on the canvas row the app draws it at.

That run was marginal on optics, not on code. Measured on the board that afternoon, projected black read 152-174 against projected white at about 173, roughly twenty gray levels with a per-pixel standard deviation near 4. On twenty consecutive frames under those conditions, unequalized detection found all four markers on 0, equalized detection at clip 8 and 16 tiles found all four on 20 in one lighting state and on 1 in a slightly brighter one, with single markers dropping in and out; multi-frame accumulation is what closed that gap. Turning off the lights above the whiteboard and raising projector brightness remains the highest-value change available, and no exposure, gain, or white balance control was touched to obtain these numbers.

A separate live UVC rate check captured 60 frames after five warm-up frames at MJPEG 1280×720: 29.95 fps, median frame interval 33.42 ms, maximum 35.40 ms. This supports about five frames within the configured 180 ms solo observation window under the sampled conditions. It does not measure Wi-Fi acknowledgement delay, optical laser settling, or projector latency. The capture was released and no exposure controls were changed.
